# Модель угроз PIN-кода

Статус: принятая базовая модель для усиления PIN-кода.

Дата: 2026-07-01.

## Назначение

Локальный PIN-код - это дополнительный браузерный слой защиты локально сохраненных данных фронтенда. Он не заменяет backend-аутентификацию, отзыв backend-сессий или защиту устройства на уровне ОС.

## Цели безопасности

- PIN, производные ключи, master key, счетчик ошибок и lockout metadata не отправляются на backend.
- Установка и ввод PIN работают без интернета после того, как app shell уже доступен локально.
- Backend-данные, сохраненные фронтендом, хранятся зашифрованно до успешного ввода PIN.
- Чувствительные локальные данные хранятся зашифрованно или удаляются.
- Пока приложение заблокировано PIN-кодом, чувствительный кеш не отображается.
- Пока приложение заблокировано PIN-кодом, фронтенд не вызывает `me`, `refresh` и другие domain endpoints.
- В приложении нет циклических фоновых backend-запросов.
- Настоящий backend logout четко отделен от локальной очистки данных.

## Не цели

- Локальный PIN не защищает от пользователя, который полностью контролирует browser runtime.
- Локальный PIN не делает browser storage защищенным от изменения.
- Локальный PIN не отзывает backend-сессии offline.
- Локальный PIN не защищает уже отображенные в разблокированном UI данные от просмотра через DevTools.

## Модель атакующего

### В зоне покрытия

- Кто-то открывает приложение в том же browser profile после того, как пользователь оставил устройство.
- Кто-то читает локальное persistent storage browser profile, пока приложение заблокировано.
- Приложение запускается offline и не должно раскрывать сохраненный кеш до ввода PIN.

### Вне зоны покрытия

- Пользователь или атакующий с DevTools и полным контролем origin runtime.
- XSS или вредоносное расширение, выполняющее JavaScript в origin приложения.
- Модифицированный браузер, измененный bundle, измененное системное время или отредактированные IndexedDB/localStorage/cookies.
- Скомпрометированная ОС или физический доступ к диску вне browser protections.
- Компрометация backend.

## Ограничения браузера

В чистом web frontend нельзя гарантировать:

- "Пользователь не может никак повлиять, даже через DevTools."
- "Счетчик неверных попыток нельзя изменить или сбросить через DevTools."
- "Этап подтверждения PIN нельзя обойти через DevTools."
- "Настоящий logout возможен offline, если токены лежат в `Secure; HttpOnly` cookies."

Причина: JavaScript не может запретить владельцу браузера смотреть или менять local origin storage и runtime state. JavaScript также не может читать или удалять `HttpOnly` cookies, а offline JavaScript не может попросить backend отозвать сессию.

## Принятое направление

- Считать PIN механизмом разблокировки локального encrypted storage.
- Не сохранять raw master key в JS-readable cookies, localStorage или sessionStorage.
- Держать unlocked session key как non-extractable `CryptoKey` в IndexedDB до local lock, local data wipe или `unlockDeadlineAt`.
- Восстанавливать этот non-extractable `CryptoKey` после reload, пока unlock deadline еще валиден, чтобы reload не просил PIN.
- Не утверждать, что restore key защищен от XSS или произвольного JavaScript в том же origin.
- Реализовать lockout после неверных попыток как best-effort локальную защиту, а не tamper-proof enforcement.
- Убрать logout с PIN-locked экрана.
- Разрешать настоящий logout только online и только в разблокированном приложении.
- Опционально разрешить "очистить локальные данные на этом устройстве" в разблокированном состоянии, с явным текстом, что backend-сессия остается активной до server logout или истечения cookie.

## Более сильные альтернативы

Если tamper-proof поведение остается обязательным продуктовым требованием, нужен один или несколько вариантов:

- backend-enforced lockout/session policy;
- WebAuthn/platform authenticator;
- native desktop/mobile wrapper с OS keystore;
- server-side encrypted data model, где фронтенд не может расшифровать данные без server grant.

## Следствия для реализации

- `Secure; HttpOnly` auth cookies остаются под контролем backend.
- Настоящий offline logout невозможен из frontend-кода.
- Установка PIN не должна зависеть от сети.
- Lockout metadata можно хранить локально только как best-effort/tamper-evident state.
- Документация и UI copy не должны обещать защиту от DevTools или полного контроля локального runtime.
